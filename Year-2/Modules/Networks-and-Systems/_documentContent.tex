\subsection{Introduction, Threat Modelling, and Applied Cryptography}

\subsubsection{Basic Definitions}

\definition{Adversary or Threat Model}{A system's security depends on the definition of the \underline{adversary}: who they are, what they can do (or their capabilities) and their determination (time, money, resources). This is the \underline{adversary} or \underline{threat model}.}

\separate{7}\definition{Asset}{An \underline{asset} is something that is worth protecting.}

\separate{7}\definition{Threat}{A \underline{threat} is a person or program that may try and access/steal your assets.}

\separate{7}\definition{Assumptions}{An \underline{assumption} is something you are relying on to be true/secure by default.}

\separate{7}\definition{Goals}{Your \underline{goal} should be in terms of what needs to be secure, and how long for.}

\separate{7}\definition{Controls}{The \underline{controls} are the things you can do to attempt to protect your assets.}

\separate{7}The CIA triad are the three main security properties, these are:
\begin{itemize}
    \item \definition{Confidentiality}{\underline{Confidentiality}: The outcomes of different actions in the system are only visible by authorised subjects.}
    \item \definition{Integrity}{\underline{Integrity}: Actions modifying the system can only be performed by authorised subjects.}
    \item \definition{Availability}{\underline{Availability}: Subjects can perform all actions they are authorised for.}
\end{itemize}
In addition to these properties, it is also important to consider additional properties, such as:
\begin{itemize}
    \item \definition{Authenticity}{\underline{Authenticity}: An entity is who they claim they claim to be.}
    \item \definition{Non-Repudiation}{\underline{Non-Repudiation}: An actor cannot easily deny that an action has occurred.}
    \item \definition{Context-Binding}{\underline{Context-Binding}: An action is valid only for a particular period of time, distance, location, and/or environment.}
\end{itemize}

\separate{7}\definition{Exploit}{An \underline{exploit} is a piece of code, a tool, or a technique that takes advantage of a flaw in software, hardware, or a network to cause unintended behaviour.}

\separate{7}\definition{Vulnerability}{A \underline{vulnerability} is a weakness or flaw in a system's design, implementation, operation, or human behaviour that an attacker can exploit to compromise security.}

\separate{7}\definition{Risk}{\underline{Risk} is the probability or liklihood that a threat will exploit a vulnerability and cause harm, loss, or negative consequences to an asset.}

\subsubsection{STRIDE Modelling}

\definition{STRIDE}{One method of classifying security risks is STRIDE, which was first developed by Microsoft. It is separated as follows:
\begin{itemize}
    \item \definition{Spoofing}{\underline{\textbf{S}poofing} is the act of using someone else's credentials to perform an operation and is a failure of identification and authentication.}
    \item \definition{Tampering}{\underline{\textbf{T}ampering} is the malicious modification of data and is a failure of integrity and authenticity.}
    \item \definition{Repudiation}{\underline{\textbf{R}epudiation} is the act of denying having performed an operation and is a failure of accountability and identification.}
    \item \definition{Information Dislosure}{\underline{\textbf{I}nformation Dislosure} is the exposure of information to unauthorised users and is a failure of confidentiality.}
    \item \definition{Denial of Service}{\underline{\textbf{D}enial of Service} is the act of denying service to legitimate users and is a failure of availability.}
    \item \definition{Elevation of Privilege}{\underline{\textbf{E}levation of Privilege} is an instance of an unprivileged user gaining privileged access and is a failure of confinement and authentication.}
\end{itemize}
This is a helpful model for structuring the analysis of potential system threats but it is not exhaustive or exclusive.}

\subsubsection{Applied Cryptography}

\definition{Encoding}{To \underline{encode} some given data, it is transformed from one format/domain to another. This is fully reversible, and does not provide any secrecy. The inverse procedure is called \underline{decoding}.}
\begin{itemize}
    \item \definition{Steganography}{A subtype of encoding is \underline{steganography}, where the existence of the secret message is concealed.}
\end{itemize}

\separate{7}\definition{Hashing}{To \underline{hash} some given data, it is transformed into a (usually) smaller, fixed-size. This is most commonly considered a one-way function. An example of this are SHA algorithms.}
\begin{itemize}
    \item A hashing algorithm works by taking a message \(m\) and applying a hashing algorithm \(h=H(m)\). \(h\) can then be sent securely and the recipient can then take \(h'=H(m')\) where \(m=m'\), and if \(h'=h\), then the message recieved is correct. 
\end{itemize}

\separate{7}\definition{Encryption}{Non-secret data (plaintext) can be \underline{encrypted} into ciphertext using a secret key. The output is \(Enc(m, K) = c\). The inverse procedure, \underline{decryption}, again uses a secret key to transform the ciphertext back to plaintext \(Dec(c, K)  = m\).}

\subsubsection{Cipher Examples}

\separate{7}\definition{Substitution Ciphers}{A \underline{substitution cipher} works by taking each letter in the alphabet and replacing it with another one. This was purportedly created and used by Julius Caesar. These are weak though and can be broken by:
\begin{itemize}
    \item \definition{Brute-Force Attack}{A \underline{brute-force} attack tries every possible key, which for substitution ciphers becomes trivial.}
    \item \definition{Frequency Analysis}{A \underline{frequency analysis} attack matches the ciphertext to the known frequency of English letters.}
\end{itemize}}

\separate{7}\definition{Vigenere Cipher}{Another historical example of a cipher is a \underline{Vigenere cipher}. This uses a sliding password, such that repeats of the same letter are coded differently. Attacks against this have to guess possible key lengths and then try all possibilities using frequency analysis. This is much harder to break.}

\separate{7}\definition{One Time Pad}{Another encryption method is using \underline{one time pads}. Here, you select a key as long as your message. Data is converted into binary and bitwise XORed with the key. To decode it, you then bitwise XOR the ciphertext with the key. This is considered theoretically secure as long as the key generation process is truly random, the key is never reused, and the key is kept secret.}

\separate{7}\definition{Stream Ciphers}{\underline{Stream ciphers} use a short secret key and a nonce - a use-once but public value - to generate a long pseudorandom sequence called a keystream. Only the short secret key must be kept private. We then XOR with the message and keystream.
\begin{itemize}
    \item To encrypt, you take the secret key \(K\) and the nonce \(N\) and feed them through a keystream generator. The resulting keystream \(S\) is then XORed with the plaintext \(p\) to produce ciphertext \(C\).
    \item To decrypt, the recipient takes the same secret key \(K\) and nonce \(N\), feeds them through the keystream generator and then XOR the result with the ciphertext \(C\) to produce the original plaintext \(p\).
\end{itemize}}

\separate{7}\definition{Block Cipher}{\underline{Block ciphers} transform a fixed-size block of plaintext into a ciphertext block of the same size, using a secret key. Encryption applies a keyed transformation to the plaintext block, and decryption reverses the transformation using the same key. An example of this is AES encryption. To encrypt longer messages, we use a mode of operation which specifies how to encrypt message blocks in sequence - this usually involves a nonce (initialisation vector).
\begin{itemize}
    \item \definition{AES-ECB}{\underline{AES Electronic Code Book (ECB) mode} works by taking the plaintext, splitting it into blocks, and then encrypting each of them separately. This is not secure.}
    \item \definition{AES-CBC}{\underline{AES Cipher Block Chaining (CBC) mode} splits the plaintext into blocks and encrypts the first one. The result is then XORed with the second plaintext block before it is encrypted, and so on.}
\end{itemize}}

\subsubsection{Public Key Cryptography}

\definition{RSA}{\underline{Rivest, Shamir, Adelman (RSA)} is an algorithm where person A computes the product of two prime numbers \(n=p \times q\) and makes the value of \(n\) public. Person A then generates a public value \(e\) and a private value \(d\) using \(p\) and \(q\). \(e\) can then be used to encrypt messages to send to person A, and \(d\) used to decrypt them. This is secure based on the computational difficulty of factorisation, but with the rise of quantum computing, is becoming less secure.}

\separate{7}\definition{Digital signatures}{\underline{Digital signatures} enables others to check that a message was signed using a private key and has not been altered. To sign a message, the sender uses their private key, and then sends the message and signature to the recipient. To verify the signature, the recipient uses the sender's public key and compares the result to the message.}

\subsection{System Security}

\subsubsection{Analysing the Security of Systems}

\definition{System}{A \underline{system} is a set of components that interact to achieve a purpose. It generally consists of five components:}
\begin{itemize}
    \item \definition{Subjects}{\underline{Subjects} are active entities with an identity and capabilities.}
    \item \definition{Resources}{\underline{Resources} are passive entities with an identity and properties.}
    \item \definition{Actions}{\underline{Actions} are interactions between subjects and resources.}
    \item \definition{Purpose}{The \underline{purpose} of a system is what it is used for, and so what security must preserve.}
    \item \definition{Boundary}{A \underline{boundary} defines what is inside (what you control), and what is outside.}
\end{itemize}

\separate{7}When considering the security of a system, we should consider four questions:
\begin{itemize}
    \item \textbf{What matters?} An asset and a security property (e.g., confidentiality).
    \item \textbf{Who could cause harm?} An adversary with stated capabilities.
    \item \textbf{Why could they succeed?} A weakness and the assumptions it violates.
    \item \textbf{What changes the outcome?} Controls and countermeasures. What is the remaining risk?
\end{itemize}

\separate{7}\definition{Trust boundary}{A \underline{trust boundary} is where data or control passes between parties that trust each other differently (e.g., a phone to a ticketing service).}

\separate{7}\definition{Attack surface}{An \underline{attack surface} is every entry point an adversary can reach.}

\separate{7}\definition{TCB}{A \underline{trusted computing base (TCB)} is what must work correctly for the goal to hold. If any part fails, security fails.}

\separate{7}\definition{Reference monitor}{A \underline{reference monitor} sits between the subjects and objects. It recieves requests for the objects, compares them with the security policy, and if it passes, returns the requested objects. It is important when designing a system that this is always invoked, it is tamper-proof, and that the check is verifiable.}

\separate{7}\definition{Kill chain}{It can also be useful to consider system security from an adversarial perspective. To do this, people commonly use the \underline{kill chain} model.
\begin{itemize}
    \item Reconnaissance: Harvesting email addresses, conference information, etc.
    \item Weaponisation: Coupling an exploit with a backdoor into a deliverable payload.
    \item Delivery: Delivering a weaponised bundle to the victim via email, USB, etc.
    \item Exploitation: Exploiting a vulnerability to execute code on the victim's systems.
    \item Installation: Installing malware on an asset.
    \item Command and Control (C2): Setting up a control channel for remote manipulation of victims.
    \item Actions on Objectives: With \say{hands on keyboard} access, intruders can accomplish their original goals.
\end{itemize}}

\separate{7}\definition{Reconnaissance}{\underline{Reconnaissance} can be split into a few types: \underline{passive gathering} where attackers have no interaction with the target, \underline{active gathering} where they do, and \underline{open-source intelligence (OSINT)} where the attacker analyses data from publically available sources. They do this to identify potential attack vectors.}

\separate{7}\example{British Library}{The \underline{British Library attack} in 2023 can be split into the categories shown in the Kill chain:
\begin{itemize}
    \item Reconnaissance: Hostile reconnaissance on the 25th-26th October was detected and blocked, but treated as a one-off.
    \item Delivery and Exploitation: Most likely privileged credentials obtained by phishing or brute force, then used on a remote-access server without MFA. No software exploit was needed.
    \item Installation and C2: The attackers hijacked the network's own administration tools, and deleted log files to cover their tracks.
    \item Actions on Objectives: A \say{historically complex} legacy network let them reach well beyond the entry point and roughly 600 GB was copied. The servers were then encrypted or destroyed.
\end{itemize}}

\subsubsection{Defence}

\definition{Asymmetry in Security}{\underline{Asymmetry in security} is the principle that finding a hole is much easier than securing all possible holes. However, an attack is a sequence of stages that are all opportunities to detect or stop it.}

\separate{7}\definition{Attack Trees}{An \underline{attack tree} is constructed such that: the root is the attackers' goal, the children are the different ways to achieve it, and the leaves are concrete actions. An OR node indicates that any of the children achieves the parent, while an AND node indicates that all children are required to achieve the parent. A set of leaves that satisfies the root is a complete attack.}

\separate{7}When designing a system, it is important to consider the following principles: minimise the attack surface, split your defence across many layers, assign users as few privileges as necessary, deny requests as a default reponse unless explicitly allowed, attackers will always take the weakest link, and you should always assume there will be a breach, so monitor and plan for recovery.

\subsection{Authorisation, Authentication, Accountability and Access Control}

\definition{Identification}{\underline{Identification} identifies who someone claims to be.}

\separate{7}\definition{Authentication}{\underline{Authentication} tests whether a person can prove their identity.}

\separate{7}\definition{Authorisation}{\underline{Authorisation} defines what a user is allowed to do.}

\separate{7}\definition{Access Control}{\underline{Access control} ensures that a user's authorisation is enforced on every request.}

\separate{7}\definition{Accountability}{\underline{Accountability} ensures that actions can be traced back to the user.}

\subsubsection{Authentication}

\definition{Authentication Lifecycle}{The \underline{authentication lifecycle} is separated into five steps. These are:
\begin{itemize}
    \item \textbf{Enrolment} binds an identity to a credential. This can go wrong if an attacker registers as you.
    \item \textbf{Authentication} requires the user to present their credentials for the verifier to check. This can go wrong after brute-force, phishing, or stolen password attacks.
    \item A \textbf{session} sets up a token to stand in for you on every later request. This goes wrong if a stolen cookie skips the login entirely.
    \item \textbf{Recovery} regains access when a credential is lost. This can go wrong if there are guessable security questions, or by exploiting the help-desk.
    \item \textbf{Revocation} removes access when people leave, or when credentials leak. This goes wrong if old codes still work.
\end{itemize}}

\separate{7}\definition{MFA}{\underline{Multi-factor authentication} can make a system more secure. The factors you can use are: something you know; something you have; and something you are.}

\separate{7}\definition{FAR/FRR}{No authenticator is perfect, we can judge their accuracy by measuring their \underline{false} \underline{acceptance rate} and \underline{false rejection rate}. 
Generally, lowering one raises the other.
For example, touch ID has a FAR of \(1:50,000\) and face ID has a FAR of \(1:1,000,000\).}

\separate{7}\definition{Similarity Score}{Each authentication attempt gives a \underline{similarity score}, not a boolean value. The threshold (visualised in \elemref{fig:Threshold Trade-off.}{Figure}\footnote{Image taken from \hyperref[cit:The Threshold Trade-Off]{Deparment of Computer Science (2026)}.}) turns it into a decision.
If we raise the threshold, then there will be fewer false accepts, but more false rejects, and vice-versa.}

This is good for comparing systems, but is rarely the right operating point.
The right setting depends on what each error costs.}

\subsubsection{Authorisation and Access Control}

\definition{Access Control Approaches}{\underline{Access control} can be implemented using one of the following approaches:
\begin{itemize}
    \item\underline{Discetionary (DAC)} where the owner decides who gets access. 
        Examples of this are Unix permissions, Windows ACLs, or sharing a Google Doc.
        It is flexible, but anything running as you, including malware, can give your data away.
    \item\underline{Mandatory (MAC)} where a system-wide policy decides and users cannot override it, even for files they create.
        Examples include government classifications or SELinux.
        It is rigid byt contains Trojan horses and careless users.
    \item\underline{Caoabilities} where unforgeable tokens are held by subjects. 
        It is good for delegation or distributed systems, but can lead to issues with revocation.
    \item\underline{Role-Based (RBAC)} where permissions attach to roles which are assigned to users.
        Joins, moves, and leaves change one assignment, rather than hundreds of permissions.
    \item\underline{Attribute-Based (ABAC)} where you decide the access from attributes of the subject, the object, the action, and the environment.
        This is good because it is fine-grained and context aware, but can lead to compications when trying to work out who can access a given file.
\end{itemize}}

\noindent An important principle is that users with a set access level cannot read up (you can only read an object if your clearance is \(\geq\) its classification), and cannot write down (write an object only if its classification \(\geq\) your clearance.)

\separate{7}Access control can fail when: the user is logged in, but nobody checks that this record is theirs;
admin pages are protected only by hiding the link from the menu;
or a role/price is in a hidden field, cookie, or JavaScript.

\subsubsection{Accountability}

When maintaining a system you should have methods for automatically logging: logins (successes and failures); MFA changes, password resets and recovery; role/permission changes; access to sensitive objects and denied requests; and administrative actions.

These logs should be protected by placing them off the host and making them append-only. 
They should also either use synchronised clocks, or there is no timeline, and should have an alert on patterns. 
They should also not allow any shared accounts.

\subsection{Network Security}

When using a network, each hop gives an opportunity for an attacker to read (confidentiality issue), change (integrity issue), drop or flood (availability issue), or fake (authenticity) your traffic.

\separate{7}These attackers can take one of three forms:
\begin{itemize}
    \item \definition{Off-path}{An \underline{off-path attacker} is not on your path.
        They can send packets with any source address, but cannot see the replies.}
    \item \definition{On-path}{A \underline{on-path attacker} sees every packet. 
        They can read, modify, drop, inject, and/or replay.}
    \item \definition{Volumetric}{A \underline{volumetric attacker} needs no cleverness, it just sends more traffic than a target system can handle.}
\end{itemize}

\subsubsection{Protocols}

Each layer of the network stack wraps the one above it in its own header (e.g., data \(\rightarrow\) TCP segment \(\rightarrow\) IP packet \(\rightarrow\) WiFi or Ethernet frame). 
A header is just bytes that the sender wrote. 
The original protocols check for accidents (checksums), but these are not necessarily for security.
The security was instead added later at different layers:
\begin{itemize}
    \item The application layer: DNSSEC (signed DNS answers) and HTTPS.
    \item The transport layer: TLS.
    \item The network layer: IPsec, WireGuard (VPNs).
    \item The link layer: WPA2/WPA3 (WiFi).
\end{itemize}

\separate{7}UDP uses a \say{fire and forget} approach to communication.
It has no connection, no ordering, and no retransmission.
Examples of its implementations include in DNS, NTP, video calls, and games.

Conversely, TCP is a reliable byte stream.
It uses handshakes, sequence numbers, acknowledgements, and retransmission.
It is used by the web, email, and SSH.

\separate{7}\definition{3-Way Handshake}{The handshake system that TCP uses is called the \underline{three-way handshake}.
In practice, it uses the following steps:
\begin{enumerate}
    \item The client sends a \textit{synchronise} \(SYN\) request with a sequence number \(x\).
    \item The server responds with a \textit{synchronise acknowledgement} \(SYN-ACK\) with a sequence number \(y\) and an acknowledgement number \(x+1\).
        An acknowledgement \(ACK\) says \say{I have everything up to here}, so each side proves it saw the other's number.
        Each side counts its bytes from its own random start.
    \item After the \(SYN\), the system must remember the client. 
        It does this by keeping one slot in its queue for half-open connections.
    \item Once the client recieves the \(SYN-ACK\) they send one more \(ACK\) with acknowledgement number \(y+1\) before sending the data.
        This means that if \(y\) is guessable, an attacker that never sees the \(SYN-ACK\) can still send the right \(ACK\).
\end{enumerate}}

\definition{DNS Record Types}{DNS records are stored in one of a few set types which provide various information about a target host. The common types are:
\begin{itemize}
    \item \underline{Address (A) records} which give the IP address for the host.
    \item \underline{AAAA records} which provide an IPv6 address for the host.
    \item \underline{Cannonical name (CNAME) records} which map one name to another and is used for redirection.
    \item \underbar{Mail exchange (MX) records} which the server uses for sending/recieving emails.
    \item \underline{Nameserver (NS) records} which indicate the authoritative DNS server for this domain.
\end{itemize}}

\subsubsection{Flooding Attacks}

\definition{DoS}{\underline{Denial-of-service} attacks max out the bandwidth of a service using UDP floods, reflection, and amplication.
The attack also manipulates the states by maliciously filling up look-up tables using DNS cache poisoning and SYN floods.
It achieves the denial of service by making each request expensive for the application using HTTP floods on search/login pages.
The attack becomes \underline{distributed (DDoS)} when thousands/millions of sources, either hijacked devices or innocent servers, are used to make the requests.}

\separate{7}\definition{DNS Cache Poisoning}{A \underline{DNS cache poisoning attack} is used by an off-path attacker who waits for a resolver to make a request to a server, before then flooding the resolver with forged answers before the real one arrives.}

\separate{7}\definition{DNSSEC}{The \underline{DNSSEC} system uses the .root's \(DNSKEY\) (the root key, KSK-2024) which is used to vouch for .com which has a \(DS\) from .root.
Then, example.com uses the \(DS\) from .com which authenticates it. 
This system provides origin authentication and upkeeps the integrity of answers.
However it does not provide confidentiality, availability, or protection for the last hop.}

\separate{7}\definition{SYN Flood}{A \underline{\(SYN\) flood attack} floods a server with \(SYN\) requests with random, spoofed sources.
These are cheap to send as they consist of one packet and don't require a reply, but they are costly to recieve as each \(SYN\) holds a queue slot until it times out.
Once the queue fills up, genuine users will be turned away.

This can be prevented by remembering nothing after a request. Instead, the system designs its sequence number \(y\) to be 32-bits, split into \(t\) which is 5 bits, \(MSS\) which is 3 bits, and then \(MAC\) which is constructed from a secret, the client IP, the client port, the server IP, the server port, and \(t\).
This means that when a \(SYN\) arrives, the server replies with \(y\) and stores nothing.
A real client would then return \(ACK = y+1\).
The server can then reconstruct the \(MAC\), and if they match it will establish the connection.}

\subsubsection{Cryptography on the Wire}

On a network, cryptography is applied in many layers: WiFi (WPA2/WPA3) acts between you and the router; a VPN tunnel acts between you and a VPN server; TLS (HTTPS) works all the way between you and the server; and DNSSEC works between you and the ISP.

\separate{7}\definition{TLS}{\underline{TLS} acts as the security layer between HTTP and TCP/IP. 
It ensures confidentiality by encrypting traffic, provides integrity by detecting any changes in transit (AEAD), and authenticates the server by adding a certificate to prove that you reached the name you asked for.
It also uses a handshake algorithm, called the \underline{TLS 1.3 handshake}:
\begin{enumerate}
    \item The browser sends a \textit{ClientHello} with a key share and cipher suites.
    \item The server then responds with \textit{ServerHello} with a key share.
    \item These two shares are used to create a shared key where the key parameters are unique to the session and deleted post-use.
        Stealing the server's key later does not decrypt today's traffic.
    \item The server then uses this shared key to send \textit{Certificate}, \textit{CertificateVerify}, and \textit{Finished}.
    \item The browser then also sends \textit{Finished}, followed by the application data.
\end{enumerate}}

\separate{7}TLS fails in practice when it is implemented wrongly, if the certificate authorities cannot be trusted, if the protocols you are using are downgraded/stripped en-route, or through exploiting the users of the system.

\subsubsection{Virtual Private Networks (VPNs), Firewalls, and Segmentation}

\definition{VPNs}{\underline{Virtual private networks (VPNs)} are effectively \say{tunnels through the Internet}.
They are generally one of: 
\begin{itemize}
    \item IPsec + IKEv2 which is the standard for site-to-site communication and is built into most operating systems.
    \item TLS-based which is used by OpenVPN and many other vendors' SSL VPNs.
    \item WireGuard which is a bespoke protocol which has been used in Linux since 2020.
\end{itemize}}

\separate{5}\definition{Firewalls}{\underline{Firewalls} are a reference monitor for the network. 
It checks every incoming packet against the network policy and refuses any that don't meet the standard.
It can consist of any from: 
\begin{itemize}
    \item A packet filter which is stateless and checks each packet's addresses, ports, and protocol on its own.
    \item Connnection tracking which is stateful and remembers connections to allow replies to existing connections.
    \item The application layer which uses a proxy, NGFW, and WAF to read the content of packets, including HTTP requests, DNS queries, and users.
\end{itemize}}

\subsection{Software Security}

\subsubsection{Software Attackers}

\definition{Remote Software Attacker}{A \underline{remote software attacker} sends input that controls any bytes the program reads: packets, form fields, files, headers, and/or log lines.
Examples of this include Heartbleed, SQL injection, and LogShell.}

\separate{7}\definition{Local Software Attacker}{A \underline{local software attacker} is on the machine and already runs as an ordinary user or app, and wants more privilege.
Examples of this include PwnKit, kernel bugs, and phone jailbreaks.}

\separate{7}\definition{Upstream Software Attacker}{An \underline{upstream software attacker} is in the supply chain and gets code into your program before you run it, e.g., a library, build server, or update.
Examples of this include XZ Utils, SolarWinds, and npm worms.}

\subsubsection{Memory Safety}

\definition{Buffer Overflow}{A \underline{buffer overflow attack} is where an attacker sends a too large input, running straight over the return address.
This means that the attacker can choose the bytes and point the new return address wherever they like.
When the input function finishes, the attacker, rather than the programmer, decides what runs next.}

\separate{7}Some other common main memory bugs are:
\begin{itemize}
    \item \textit{Out-of-bounds read}, where the input reads past the end of a buffer, such as with Heartbleed or Crowdstrike.
    \item \textit{Integer overflow}, where a number wraps around, often a size, such as with Stagefright.
    \item \textit{Format string}, where an input becomes printf's instructions, such as the iPhone Wi-Fi name.
    \item \textit{Use after free}, where memory is used after it was given back, such as with many browser zero-days. 
\end{itemize}

\separate{7}Developers can mitigate the risks of these attacks by implementing:
\begin{itemize}
    \item \textit{Stack canary}, where a random value below the return address is checked before returning.
        If it has changed, then the program stops.
    \item \textit{No-execute (NX)}, where data areas are marked as not runnable, so smuggled bytess will not run.
    \item \textit{ASLR}, where everything loads at random places each run.
    \item \textit{Control-flow checks}, such as in newer CPUs, which keep a protected copy of each return address.
\end{itemize}

\subsubsection{Injection}

To prevent SQL injections, code and data should be kept apart.
The query's structure should be fixed first and then the values should travel separately and are only ever data.
Similarly, least privilege and a web application firewall should be implemented to restrict what the web app is allowed to run.

\subsubsection{Finding and Fixing}

A vulnerability falls into one of 5 lifecycle stages: the bug is first written, the bug is found, the vendor is told about the bug, a patch is released, the patch is installed.

\subsubsection{Digital Forensics}

When examining an incident, you should never change data that may be relied on in court.
If you must touch originals, be competent, and able to explain what your actions did.
Keep an audit trail -- an independent examiner should get the same result.
The person in charge is responsible for following the law and these principles.

Similarly, you should consider the order of volatility when collecting data about an incident.
CPU registers, cache, and memory may be replaced early, whereas temporary files, disk, remote logs/monitoring, or backups/archives will not.

Evidence of an incident can be: 
logs about who connected, when, and what they sent;
timestamps for when data was created, modified, accessed;
deleted files that have not yet been overwritten;
and metadata such as authors and edit history.

\subsection{Introduction to Networks and Basic Components}

\subsubsection{Basic Definitions}

\definition{Computer Network}{A \underline{computer network} is a group of devices that are connected to one another in order to exchange information or share resources.}

\separate{7}\definition{End Devices}{\underline{End devices} form the interface between users and the underlying communication network.}

\separate{7}\definition{Intermediary Devices}{\underline{Intermediary devices} interconnect end devices.}

\separate{7}\definition{Transmission Media}{\underline{Transmission media} provides the channels over which the message travels from source to destination. 
Data appears as signals in transmission media.}

\separate{7}\definition{Wireless Media}{\underline{Wireless media} carries signals in the electromagnetic spectrum without any physical wires.}

\subsubsection{Network Protocols}

\definition{Network Protocol}{A \underline{network protocol} defines the format and order of messages sent and recieved among network entities, and controls the actions taken on message transmisison and/or reciept.
They must account for the following requirements/rules: 
\begin{itemize}
    \item The sender and receiver must both always be identified.
    \item There must be a common language and grammar used.
    \item The messages should be delivered within a given timing/at a given speed.
    \item There must be a confirmation or acknowledgement of requirements.
\end{itemize}
Protocols are designed to deal with one or more of these five factors:
\begin{itemize}
    \item \textit{Message Timing}: 
        When someone is able to send a message; 
        how much information can be sent, and the speed at which it can be delivered; 
        and how long to wait for responses, and what action to take if a response timeout occurs.
    \item \textit{Message Delivery Options}: Unicast, multicast, or broadcast.
    \item \textit{Message Encoding}: 
        Converting information into another acceptable form for transmission.
        Decoding is to reverse the process.
    \item \textit{Message Formatting and Encapsulation}: Placing one message format inside another message format.
    \item \textit{Message Size}: Breaking a long message into individual pieces that meet both the minimum and maximum size requirements.
\end{itemize}}

\subsubsection{Access Networks}

\definition{DSL}{A \underline{digital subscriber line (DSL)} uses existing telephone lines to a central office DSLAM.
Data over a DSL phone line goes to the Internet, and voice over a DSL phone line goes to the telephone net.

It has asymmetric access, so the downstream and upstream rates are different (2.5 Mbps upsteam vs. 24 Mbps downstream).}

\separate{7}\definition{Cable Network}{The \underline{cable network} is a network of cable where fiber cables attach homes to the ISP router.
Unlike DSL, which has a dedicated access to the central office, homes share an access network that connects to a cable headend.

It uses hybrid fiber coax (HFC), which is also assymetric.
It has a 42.8 Mbps transmission rate downstream, and a 30.7 Mbps upstream rate.}

\separate{7}\definition{Ethernet}{\underline{Enterprise access networks (Ethernet)} is widely used in companies, universities, etc. 
It has a wide range of possible transmission rates (from around 10 Mbps to 10 Gbps).
Today, end systems are typically connected by Ethernet switches.}

\separate{7}\definition{Wireless Access Networks}{\underline{Wireless access networks} connect end systems to a router wirelessly via a base station (a wireless access point).

These networks can either be: 
a LAN (local-access network), which is typically within one building, and uses WiFi to provide a fast transmission rate; 
or a WAN (wide-area network), which is typically provided by a telco (mobile) operator over 10's of kilometers, and thus generally has a much slower transmission rate.}

\subsubsection{Network Security}

\definition{Packet Sniffing}{\underline{Packet sniffing} is an attack where some network interface reads/records all packets passing by on the network.
An example of this is Wireshark.}

\subsection{Core Concepts of Computer Networks}

\subsubsection{Switching}

\definition{Circuit Switching}{Two network nodes establish a dedicated communication channel (called a circuit) before the nodes can communicate.
Users will remain connected to, and enjoy the full bandwidth of, the channel until the session is terminated.
This is called \underline{circuit switching}.}

\separate{7}\definition{Packet Switching}{Two network nodes do not establish a dedicated communication channel.
Instead, transmission links are shared by mutiple users.
End devices break application data into small pieces for transmissions.
This means that different pieces may take different paths to reach the destinations.
This is called \underline{packet switching}.}

\subsubsection{OSI Reference Model}

\definition{OSI Model}{The \underline{open systems interconnection model (OSI model)} is split into seven layers, where each layer provides some functionality to the upper layers and relies on the lower layers.
The upper layers are more concerned with user services and applications, while the lower layers are more concerned with hardware and the actual transmission of data.}

\separate{7}A general summary for each of the layers' purpose is that:
\begin{itemize}
    \item \textit{Application layer} handles emails, web browsers, file transfers, etc.
    \item \textit{Presentation layer} translates data formats, implements data encryption/decryption, etc.
    \item \textit{Session layer} establishes/terminates sessions and synchronises communicating nodes.
    \item \textit{Transport layer} supports communications between diverse applications across diverse networks.
    \item \textit{Network layer} determines the best path through the network.
    \item \textit{Data-link layer} defines frames, detects and manages collisions, and handles error detection.
    \item \textit{Physical layer} manages the physical medium and signal transmissions.
\end{itemize}

\separate{7}\definition{Protocol Encapsulation}{On the sender side, they generally only see:
data, which is the application layer;
segment (TCP) and datagram (UDP), which is the presentation, session, and transport layer;
packet, which is the network layer; 
frame, which is the data-link layer;
and bit, which is the physical layer.

This practise is known as \underline{protocol encapsulation}.
Similarly, on the reciever side, their system performs \underline{protocol de-encapsulation} to split these groupings back into the original layers.}

\subsubsection{Data Routing and Forwarding}

\definition{Routing}{Routers determine the next hop (router) on which to send a piece of data.
This is known as \underline{routing} and is determined by considering delays, error rates, energy consumption, etc.
These routers then record these hops and associated interfaces in their routing tables.}

\separate{7}\definition{Forwarding}{\underline{Forwarding} is where intermediary network devices move a piece of data from one interface to another interface.}

\separate{7}\definition{Switch}{A \underline{switch} implements data forwarding.
It does this by checking if the given source address is in its form switching tables (based on MAC addresses).
If not, it adds the source address and the port.

It then inspects the destination address to see if there is a port associated with that address in the table.
If not, it forwards the data to all the ports.
However, only the real destination will process the packet, meaning that all the other nodes will discard the packet except for the correct node.}

\separate{7}\definition{Store and Forward}{\underline{Store and forward} is a telecommunications technique in which an intermediary device keeps information and sends it at a later time to the destination, or to another intermediary device.}

\separate{7}\definition{Nodal Processing Delay}{\underline{Nodal processing delay} is the time spent on checking bit errors and determining output link, and is generated by intermediary devices.}

\separate{7}\definition{Queueing Delay}{\underline{Queueing delay} is the time taken at routers waiting to be routed.
For a router, if the data input rate exceeds the data output rate for a period of time, then packets will queue.
If the queue fills up, then packets can be dropped and must be retransmitted by the previous node, or by the source.}

\separate{7}\definition{Transmission Delay}{\underline{Transmission delay}, also known as \underline{store-and-forward delay}, is the amount of time required to push all the bits in a piece of data onto the wire.
For a \(L\)-bit packet, it will take \(\frac{L}{R}\) seconds to transmit at \(R\) bits per second.
This means that the end-to-end delay will be \(2 \frac{L}{R}\).}

\separate{7}\definition{Propagation Delay}{\underline{Propagation delay} is the time required to travel through the medium (i.e., wires).}

\separate{7}This means that the packet delay can be calculated using
\begin{equation}
    d_p = d_{proc} + d_{queue} + d_{trans} + d_{prop}
\end{equation}
where \(d_{proc}\) is the nodal processing delay, \(d_{queue}\) is the queueing delay, \(d_{trans}\) is the transmission delay, and \(d_{prop}\) is the propagation delay.

\subsection{Application Layer}

\subsubsection{Network Application Architecture}

\definition{Processes}{\underline{Processes} are programs running within a host.
Within the same host, two processes communicate using inter-process communication (defined by the OS).
Processes on different hosts communicate by exchanging messages.}

\separate{7}\definition{Socket}{A \underline{socket} is a software mechanism that allows a process to create and send messages into, and recieve messages from, the network.}

\subsubsection{Protocols}

\definition{TCP}{The \underline{TCP} protocol provides the following services:
\begin{itemize}
    \item \textit{Connection-Oriented}: Setup required between the client and server processes.
    \item \textit{Reliable transport} between the sending and recieving processes.
    \item \textit{Flow Control}: The sender won't overwhelm the reciever.
    \item \textit{Full-Duplex Connection}: The connection can send messages in both directions at the same time.
    \item \textit{Unreliable data transfer} between the sending and recieving processes.
        \begin{itemize}
            \item It does not provide reliability, flow control, congestion control, security, or connection setup.
        \end{itemize}
    \item \textit{Short-delay transmissions} between sending and recieving processes.
\end{itemize}}

\separate{7}\definition{HTTP}{\underline{HTTP (Hypertext transfer protocol)} is an application-layer protocol for web services that uses a client-server model where the client is a browser that requests, recieves, and displays web objects; and the server is the web server that sends objects in response to requests.

The protocol achieves this using the transport layer:
\begin{itemize}
    \item The client initiates a TCP connection to the server on port 80.
    \item The server accepts the TCP connection from the client.
    \item HTTP messages are exchanged between the browser and the web server.
    \item The TCP connection is closed.
    \item HTTP is stateless as the server maintains no information about past client requests.
\end{itemize}}

\separate{7}\definition{Non-Persistent HTTP}{\underline{Non-Persistent HTTP} is a form of the HTTP protocol where at most one object is sent over the TCP connection, the connection is then closed, which means that downloading multiple objects requires multiple connections.
For example,suppose a user enters a URL then,
\begin{enumerate}
    \item The HTTP client initiates a TCP connection to the HTTP server on port 80.
    \item The HTTP server at host is waiting for TCP connections on port 80 and accepts the connection, notifying the client.
    \item The HTTP client sends a HTTP request message into the TCP connection socket. 
        The message indicates that the client wants the given URL.
    \item The HTTP server recieves the request message, forms a response message containing the requested object, and sends the message into its socket.
    \item The HTTP server closes the TCP connection as soon as the client recieves the response intact.
    \item The HTTP client recieves the response message containing the HTML file and displays it.
    \item Steps 2-6 are repeated for each of the objects requested by the client.
\end{enumerate}
The response time for these requests is \(2 RTT + FTT\), where \(RTT\) is the round trip time, and \(FTT\) is the file transmission time.}

\separate{7}\definition{Persistent HTTP}{\underline{Persistent HTTP} is a form of the HTTP protocol where multiple objects can be sent over a single TCP connection between the client and the server.
It has a response time of \(RTT + FTT\), assuming that connections to the server have already been established, and that all files are requested in parallel.}

\subsection{Transport Layer}

\subsubsection{Transport Layer Services}

The transport layer primarily uses transport control protocol (TCP) and user datagram protocol (UDP). 
These protocols commonly provide segmentation and logical communication services between applications running on different hosts.

\separate{7}\definition{TCP Segments}{\underline{TCP segments} use encapsulation to send information. 
This consists of three sections, with each section encapsulating the previous one:
\begin{itemize}
    \item \textit{TCP Segment}: This contains the TCP header and the TCP payload.
    \item \textit{IP Datagram}: This contains the IP header and the IP payload (this is the TCP segment).
    \item \textit{Ethernet Frame}: This contains the Ethernet header, the Ethernet payload (the IP datagram), and the FCS (the frame check sequence).
\end{itemize}}

\separate{7}\definition{UDP Protocol}{The \underline{UDP protocol} provides the following services:
\begin{itemize}
    \item \textit{Connectionless}: The data is sent directly without any handshakes between the sender and the reciever.
    \item \textit{Unreliable Data Transfer}: No datagram reordering, so there is noretransmission to recover loss or error.
    \item \textit{Many other services are reliable} as there is no flow control, congestion control, security, etc.
\end{itemize}
Typically, the UDP protocol works by:
\begin{enumerate}
    \item The client sends some data to the server.
    \item The server recieves the data and processes it.
    \item The server then sends the modified data back to the client.
    \item The client recieves the modified data.
\end{enumerate}}

\separate{7}TCP provides a reliable, in-order byte-stream transfer \say{pipe} between the client and the server.
\begin{enumerate}
    \item The server must first be running and must have created a socket that accepts the clients' connection requests.
    \item The client contacts the server by:
        \begin{itemize}
            \item Creating TCP/IP socket, specifying the IP address and the port number of the server process.
            \item When the client creates a socket, the client TCP establishes a connection to the server TCP.
        \end{itemize}
    \item When contacted by the client, the server TCP creates a new socket for the server process to communicate with that particular client.
        \begin{itemize}
            \item This allows the server to talk with multiple clients.
            \item Source port numbers are used to distinguish different processes on the same clients.
        \end{itemize}
\end{enumerate}

\subsubsection{Multiplexing}

\definition{Multiplexing}{TCP and UDP extend the IP delivery service between hosts to deliver service between processes.
\underline{Multiplexing} occurs at the sender, where data from multiple sockets is handled and the transport header is added.
At the reciever end, \underline{demultiplexing} uses the header information to deliver the recieved segments/datagrams to the correct socket.}

\separate{7}\definition{Connectionless Multiplexing}{\underline{Connectionless multiplexing} occurs when a host sends a UDP segment:
All sockets have a host-local port number and are assigned automatically, or via \textit{bind()}.

Similarly, when a host recieves a UDP segment, \underline{connectionless multiplexing} occurs where the host checks the destination port number in the datagram and directs the UDP datagram to the socket with that port number.}

\subsubsection{Reliable Data Transfer}

\definition{rdt1.0}{\underline{rdt1.0} provides reliable transfer over a reliable channel (meaning there are no bit errors, and that no packets are lost).
The sender sends data into an underlying channel and then then waits for a call from above.
Conversely, the receiver reads the data from the underlying channel and then waits for a call from below.}

\separate{7}\definition{rdt2.0}{\underline{rdt2.0} provides the same service as rdt1.0, but can now deal with bit errors.
To do this, it utilises a checksum.
When the reciever reads the message, they send an acknowledgement \(ACK\) to the sender, letting them know that the segments were recieved ok, or a negative acknowledgement \(NAK\) if not.
The sender would then retransmit the segments on receipt of a \(NAK\).

However, errors can still occur if the \(ACK\)/\(NAK\) is corrupted.}

\separate{7}\definition{ARQ}{Using \(ACK\)s and \(NAK\)s is known as \underline{automatic repeat request (ARQ) protocols}.
This process implements error detection using checksum bits and provides the reciever with feedback.}

\separate{7}\definition{rdt3.0}{\underline{rdt3.0} can also deal with packet loss.
To accomplish this, the sender starts a timer after they transmit, and if they do not recieve an \(ACK\) within a \say{reasonable} amount of time, then they retransmit the data.}

\subsubsection{Pipelined Protocols}

When using pipelined protocols:
\begin{itemize}
    \item The range of sequence numbers must be increased. 
        \begin{itemize}
            \item There may be multiple, in-transit, unacknowledged packets.
            \item Each packet will have a unique sequence number.
        \end{itemize}
    \item Multiple packets may end up buffering at the sender and/or the reciever.
        \begin{itemize}
            \item The sender buffers packets that have been transmitted but not yet acknowledged.
            \item The reciever buffers correctly recieved packets before it can process them to the upper layer.
        \end{itemize}
    \item The buffering requirements will depend on the manner in which a data transfer protocol responds to lost, corrupted, and overly delayed packets.
\end{itemize}

\separate{7}\definition{Go-back-N}{\underline{Go-back-\(N\)} is one type of pipelined protocol where the sender can send multiple packets without waiting for the \(ACK\).
The sender can have up to \(N\) unacknowledged packets in the pipeline.
The reciever only sends cumulative \(ACK\)s and doesn't \(ACK\) a packet if there is a gap.
The sender has a timer for the oldest unacknowledged packet and when the timer expires, they retransmit all the unacknowledged packets.}

\separate{7}\definition{Selective Repeat}{Another pipelined protocol is \underline{selective repeat} where the sender can have up to \(N\) unacknowledged packets in the pipeline.
The reciever sends individual \(ACK\)s for each packet.
The sender maintains a timer for each unacknowledged packet and when the timer expires, they retransmit only that unacknowledged packet.}

\subsection{Network Layer}

\subsubsection{Routing Algorithms}

\definition{Routing2}{\underline{Routing} is the process of discovering network paths.
To do this, you must decide what to optimise, model the network as a graph of nodes and links, and update the routes for changes in topology.}

\separate{7}\definition{Optimality Principle}{The \underline{optimality principle} states that: if router \(J\) is on the optimal path from \(I\) to \(K\), then the optimal path from \(J\) to \(K\) is on the same route.
This identifies the optimal path from source to destination where the distance metric is either the number of hops, or the time delay.

The \underline{sink tree} contains the optimal routes from all sources to a given destination.}

\separate{7}\definition{Dijstra's Algorithm}{\underline{Dijstra's algorithm} computes a sink tree on a graph given the following assumptions:
\begin{itemize}
    \item Each node is labelled with its distance from the source node to the best known path.
    \item Initially no paths are known.
    \item Each link is assigned a non-negative weight/distance.
    \item The shortest path is the one with the lowest total weight.
\end{itemize}
It then computes the shortest path by:
\begin{enumerate}
    \item Start with the sink, set distance at other nodes to infinity.
    \item Label each node as either tentative (\(\circ\)) or permanent (\(\bullet\)), with all nodes starting as tentative.
    \item Pick the lowest distance to a non-permanent node, and make it permanent.
    \item Repeat from this node until all nodes are permanent.
\end{enumerate}}

\subsubsection{Routing Types}

\definition{Distance Vector Routing}{In \underline{distance vector routing}, each node maintains a table (vector of best distance to the destination).
These tables are updated by exchanging information between nodes periodically.
Tables have two entries, an outgoing line and an estimated distance.

When establishing these tables: each node knows the distance of its links to its immediate neighbours.
Each node advertises a vector of the lowest known distance to all nodes.
Each node uses recieved vectors to update its own, which is repeats periodically.}

\separate{7}\definition{Link State Routing}{\underline{Link state routing} follows these steps:
\begin{enumerate}
    \item A router learns the network address of the neighbouring routers by sending a \say{HELLO} packet and records their names.
    \item It then sets the distance to each neighbour.
    \item The router then constructs a packet telling all other routers what it has just learned.
    \item It then sends the packet to, and recieves packets from, all other routers.
    \item This can then be used to compute the shortest path using Dijkstra's algorithm.
\end{enumerate}}

\separate{7}\definition{Flooding}{\underline{Flooding} is a simple method to send a packet to all network nodes. 
Each node floods a new packet recieved on an incoming link by sending it out on all of its other links.
Nodes need to keep track of flooded packets so that the flood can be stopped.
This does not rely on routing tables being built first.}

\separate{7}\definition{Hierarchical Routing}{\underline{Hierarchical routing} reduces the work of route computation but may result in slightly longer paths than flat routing.}

\separate{7}\definition{Broadcast Routing}{\underline{Broadcast routing} sends a packet to all nodes.
It uses \textit{reverse path forwarding (RPF)} where arrived packets are checked to see if they arrived from a preferred link (the link that is normally used for sending packets towards the source of the broadcast).}
